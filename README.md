## 共通制作ルール

# Playable LP 制作運用（共通ルール）

このファイルは全案件の実装・レビュー・完了判定に適用する。案件固有の目的、商品、素材、CTA、例外、比較結果は `projects/<案件ID>/brief.md` と `qa/` に保存する。追加ルールは完了済みの成果を活かして適用し、追加だけを理由に再調査・再実装しない。既存の証拠を再利用し、未確認や変更の影響がある項目だけ追加検証する。

- 各案件を `projects/<案件ID>/` に分離する。既存案件や参照元を上書きしない。
- 着手前に brief.md と status.json を読む。参照URL、目的、訴求、素材、CTA、未確認情報を記録する。
- 企画 → 制作 → QA → 修正 → 再QA → プレビュー提出を実施する。未検証を合格と記載しない。
- 操作はタッチ、マウス、キーボードに対応。開始は明示操作、スキップ・再挑戦を用意。ズームを禁止しない。
- ゲーム操作領域はテキスト選択・画像のネイティブドラッグを防止する。親LPとiframe内の両方を対象とし、連続タップ・長押し・領域境界をまたぐドラッグで青い選択表示が出ないか検証する。商品説明やフォームの通常の選択・コピー、キーボードフォーカス、ズームは維持する。
- 動作合否に加え、操作性・思わず遊びたくなる楽しさ・デザイン品質を確認する。案件ごとに有名企業のブラウザゲーム、Playable Factory事例、現行ストア上位ゲームから近い体験を選び、実操作・観察・未検証を区別して改善点を記録する。
- 参照調査は入口の分かりやすさ、初回操作への反応、直接操作の追従、成功演出、難易度、再挑戦、視覚階層、余白、文字、素材の一貫性を比較する。元体験を簡易ボタンへ劣化させない。採用/不採用の理由を残す。
- ストア順位は国・カテゴリ・確認日を記録し、タイトルの本編と広告Playableを区別する。ソースは公開・提供されているものを読み、URL/コミット/確認箇所を記録する。非公開ソースを確認済みとしない。再利用時はライセンスを確認する。
- 価格・契約・配送・効能は現行の公式情報で確認してから掲載。根拠がなければ省く。
- 工程や修正が完了するたび status.json と journal.md を更新。問題は qa/report.md に再現手順・原因・修正・再検証結果を残す。
- Chromeで正常完走、途中スキップ、再挑戦、キーボード、モバイル幅、CTA、画像、横はみ出し、コンソールを検証する。
- 自己修正は再現 → 原因特定 → 最小修正 → 同じケースを再検証。3回連続で同じ問題が解決しなければ記録し、他の独立作業を進める。
- GitHub公開や接続未確認、外部依存は明示。認証情報をファイルやログに保存しない。
- 常駐・定期実行は設定が実際に完了した場合だけ稼働中と報告する。

## 1. 元の良さを維持する

- 既存Playable改修では実際にプレイし、操作方法・演出・グラフィック・テンポを記録する。既存の実プレイ記録は再利用できる。
- こする、動かす、長押しなどの直接操作を、実装やテストを容易にするだけのボタン操作へ置き換えない。
- 元版と改修版を工程ごとに比較し、操作感・没入感・見た目が劣化していないことを完成条件にする。コード一致は実操作比較の代わりにならない。

## 2. タッチ操作の品質

- 初期実装からゲーム領域の文字・画像選択、薄青の選択範囲、選択メニュー、画像ドラッグを防止する。user-select、touch-action、標準イベントの制御は対象領域と必要な動作に限定する。
- ページ全体のスクロール・拡大、フォーム入力、商品説明のコピー、キーボード操作を無差別に無効化しない。
- タップ・連打・長押し・スワイプ・ドラッグ・領域外への指移動・操作中断を検証する。スクロールとの競合、取りこぼし、意図しない画面移動を解消する。
- 実機タッチとマウスによるモバイル幅検証を区別し、実機未検証を明示する。

## 3. 思わず遊んでしまうゲーム性

- 開始前に遊び方と楽しそうなポイントが直感的に伝わる入口を作る。
- 操作直後に見た目や動きが反応し、成功・失敗・進捗が分かるようにする。
- 単純な連打や同じ手順の反復だけにせず、ゲームに合う判断・変化・上達・達成感を設ける。難易度は数値だけでなく実際の判断や操作の変化で確認する。
- 短時間の広告体験に合う長さにする。不必要な待ち時間や繰り返しタップで進行を引き延ばさない。

## 4. デザインの品質基準

- 企業の公開ブラウザミニゲーム、https://playablefactory.com/our-works、関連ジャンルのストア上位作品から案件に合う参考例を選ぶ。
- 配色・画面構成・操作誘導・反応・演出・情報量・テンポのどこを参考にするか具体化し、制作物と見比べた品質差を改善項目にする。調査だけで終えない。
- ソース参照は公開され利用条件を確認できるものを対象とする。閲覧できないコードを確認済みにせず、ロゴ・キャラクター・固有素材を無断流用しない。

## 5. ゲーム画面はプレイ優先

- 長文、大きな説明パネル、過密なUIで操作領域を狭めない。説明は必要なタイミングで短く、操作対象の近くに置く。
- スマホで文字・対象物・ボタンの大きさと主要要素・商品画像の見切れを確認する。
- 表示確認は開始画面だけで済ませず、最長の工程見出し、ゲージ、操作ヒント、台詞、終了カードを短い画面でも確認する。要素間の重なり・枠外文字・画像の実表示サイズをスクリーンショットと実寸で確認し、DOMに存在するだけで合格にしない。
- プレイ中の商品説明・CTAの半端な露出で集中を妨げない。開始画面は原則スマホ1画面を目安に、引きの強い見出しと主役のビジュアルに絞る。

## 6. 商品説明とCTAも作り込む

- ゲーム体験から商品特徴・購入理由へ自然につなげ、説明のためだけのゲームにしない。
- 汎用カードと文章だけで済ませず、公式LP素材、図解、必要に応じた画像生成を使う。食品のおいしさ、商品の正確さ、仕組みの分かりやすさを確認し、簡単な図形だけの見た目を完成扱いにしない。
- フォント・配色・トーンをブランドと遷移先LPに合わせる。価格・割引率・単位・注釈の大きさと位置を整える。
- 価格・特典・訴求は確認できた条件に準拠し、制作メモやプレビュー用文言をユーザー画面に残さない。

## 7. 検証と完了判定

- コード確認に加え、ブラウザで開始からCTAまで実操作する。QAは次の3軸を別々に評価する。
  - 動作：進行、再挑戦、表示、リンク、パラメータ、エラー。
  - 体験：操作の分かりやすさ、反応、テンポ、楽しさ、単調さ。
  - 表現：参考作品との品質差、商品画像、文字、余白、ブランド整合性。
- 問題は修正して同じケースを再検証する。テストのためにゲーム体験を簡略化しない。
- 自己レビューで主要改善点が残る、または必要な比較が未完了なら完成扱いにしない。プレビュー提出と完成を区別する。
- 最終報告は変更内容、実際の確認範囲、未確認範囲、残課題を示す。チェック項目は `templates/qa-report.md` を案件へ適用する。

## 8. フィードバックを蓄積する

- 修正指示は案件固有か共通基準か判断し、共通基準はこのファイルとテンプレート、案件固有はbriefとQAに記録する。同じ指摘を繰り返させない。
- 案件の `journal.md` に指摘・変更・検証を残し、status.jsonに再開地点と残課題を保存する。
- 再レビュー共通補足: 進捗の疑似要素とラベル内部の重なりも対象。スキップは開始前/終了後だけでなく、プレイ中のスマホ1画面内で実際に押せるか確認する。クリック直後の古いスクリーンショットを結果にしない。
